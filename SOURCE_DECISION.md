# Single-App Source Decision — LO2 vs OTel Demo (and re-instrumentation)

## Bottom line

**Run all three methods on Nezha restricted to ONE system — Train Ticket — as the single shared app.** It is the only candidate where the load-bearing RLM property (many concurrent multi-service traces per window with `trace_id` in *every* log line) is verified from raw bytes, not docs, and a single-system slice keeps that property because the dataset is physically date-split per system (TrainTicket = `2023-01-29`/`01-30`). **LO2 is OUT:** its trace-navigation arm is *doubly vacuous* — adversarial verification **confirmed** that the per-line light-4j `correlationId` does NOT propagate cross-service (the OAuth flows make zero service-to-service HTTP calls; each request is one service → Hazelcast cache → one JDBC span to MySQL, which is exactly why Jaeger records a single span), AND the run model is strictly sequential at ~7 users, so there is no concurrency to navigate. **Re-instrumentation does NOT beat the cheaper paths:** re-instrumenting LO2 (Route B) fails at the `Http2Client`/XNIO client boundary even though the OTel agent *does* emit Undertow server spans (the researcher's "Undertow unsupported" and "bug 10323" justifications were **refuted** — but the conclusion stands via the client boundary), and re-instrumenting Train Ticket OTel-native (Route C) is weeks of polyglot build for a property Nezha already ships. The patched OTel Demo is the strongest *fallback* (native-OTLP, real distributed traces) but its Drain arm is the thinnest and it carries live-capture/build risk Nezha eliminates entirely.

**Interpretation.** The two apps are mirror images: LO2 maxes Drain and starves RLM; the OTel Demo maxes RLM/native-OTLP and starves Drain. LO2's single-span Jaeger traces make any **Jaeger/trace_id-based** navigation a literal no-op (`extract_trace_ids()` returns one ID per request). Crucially, the salvage hypothesis — "grep the per-line `cId` to recover a cross-service slice" — was **adversarially confirmed as refuted**: the light-4j `CorrelationHandler` + `Http2Client.propagateHeaders()` machinery is real but *vacuous on this topology* because no deployed OAuth service ever makes an outbound `Http2Client` call (the only cross-service HTTP code lives in `authhub`, which isn't even deployed in the dataset's `docker-compose`), and the multi-step AuthorizationCode flow is two independent Locust requests that each auto-generate a *different* `cId`. So **the correlationId does NOT rescue log-level cross-service navigation** — neither the Jaeger arm nor the log-grep arm is viable. LO2 cannot be the single app.

## The single-app constraint — who starves which method

| Candidate | Starved method | Fixable? |
|---|---|---|
| **Nezha — Train Ticket only** (recommended) | **Drain volume / label balance.** Only ~38/101 episodes (exception+return) emit ERROR logs; cpu/network faults emit zero ERROR logs (→ explicit "metrics-only" floor class); restricting to one system roughly halves usable episodes; total corpus is orders of magnitude below LO2 | **Workable, not fixable to LO2-scale.** Drain trains and yields stable anomalous templates; volume is "adequate, not high." Mitigate by reporting Drain template count + base rate and treating it as the weak arm. Per-window concurrency for RLM and ~25k-record token band for in-context are **not** starved (verified) |
| **LO2 (as-is)** | **RLM trace structure (fatally).** Single-span + per-`(run×test×service)` file isolation + sequential ~7-user runs = no many-concurrent-trace windows; correlationId doesn't propagate | **No.** The MySQL-only fan-out is architectural; fixing it requires fabricating service-to-service calls the real system never makes (destroys ecological validity). **Unfixable** |
| **Patched OTel Demo** | **Drain volume** (thin, low-cardinality) + span-only fault logs | **Partially.** Raise `LOCUST_USERS` well above the default 5 over a sustained capture (hot-path emitters help more than the call-site count implies); ~3-line `logger.Error` patches make span-only faults log-visible. Drain stays the weak arm |
| **Re-instrumented LO2 (Route B)** | **RLM trace structure** still starved | **No.** OTel agent emits Undertow *server* spans (so trace_id stamps into logs), but `Http2Client` is uninstrumented and the agent's Undertow module is server-only → no W3C propagation across the client boundary, so traces stay single-process/shallow. Even fully hand-instrumented (weeks), the MySQL-only call graph keeps RLM near-vacuous |
| **Re-instrumented Train Ticket OTel-native (Route C)** | None (best fit) | **Yes, but expensive.** 41 Spring-Boot services on RestTemplate/Feign are the agent's sweet spot, but standing up + stabilizing the polyglot stack and re-driving faults live is **weeks** |

## Recommendation & design

**Winner: Option (3) — Nezha-as-is, single system = Train Ticket, accepting CSV.** It is the only option that satisfies all three methods *without a build* and with the RLM property **verified from raw bytes**. Reject (4) LO2+correlationId (refuted — no cross-service nav, no concurrency). Reject (2) re-instrumentation: Route B (LO2) is unfixable, Route C (Train Ticket) is weeks of effort for a property Nezha already ships. Keep (1) patched OTel Demo as the **native-OTLP fallback** only, to defend against "Nezha is CSV-not-OTLP" reviewer objections.

**Concrete design for Train Ticket–only Nezha (one app, all three methods):**

- **App / source.** `git clone https://github.com/IntelligentDDS/Nezha` (MIT; cite Yu et al., ESEC/FSE 2023, doi:10.1145/3611643.3616249). Use **only** `rca_data/2023-01-29/` and `2023-01-30/` (Train Ticket; 45 services, ~79 spans/trace, ~44 logs/trace, 30 fault categories). No Docker, no K8s, no flagd, no live capture — eliminates Phase 2's entire deploy/toggle burden and every OTEL-1/OTEL-5 blocker.
- **How `trace_id` gets into logs.** Already there — verified 100% coverage. Log CSVs carry dedicated `TraceID`/`SpanID` columns (header `Timestamp,TimeUnixNano,Node,PodName,Container,TraceID,SpanID,Log`); `trace_id` is *also* redundant in the body string (`"TraceID: <id> SpanID: <id> ..."`).
- **Fault catalog + labels.** Join `2023-01-30-fault_list.json` inject episodes to windows. **Scope the log-visible class set to `exception` + `return`** (emit ERROR logs); bucket `cpu_contention`/`cpu_consumed`/`network_delay` into an explicit **"metrics-only" floor class** (verified zero ERROR logs). Root cause = **which pod/service** (exact-match at service level via `inject_pod`); do NOT claim fault-type from log text (both render as generic errors). Use `construct_data/root_cause_ts.json` for inner-region labels if finer RCA is wanted.
- **Windowing that guarantees many concurrent traces.** Each per-minute CSV *is* a window — deterministic, re-runnable. Verified for Train Ticket: 100% trace_id coverage, **~53-137 distinct concurrent multi-pod traces per window, ~7-8 pods/trace, every sampled trace spanning >1 pod**. (Note the **correction**: the headline "497 traces/window" is an *Online Boutique* figure; Train Ticket trades raw window concurrency for deeper per-trace topology. Either way RLM `extract_trace_ids()`/`lines_for_trace()` does real selective work — non-vacuous.)
- **plain / structured / structured-no-trace variants.** One mechanical `csv→OTLP-JSON LogRecord` map (`src/log_bench/data/nezha.py::to_otlp`): `TimeUnixNano→timeUnixNano`, `TraceID→traceId`, `SpanID→spanId`, severity→`severityText`/`severityNumber` (ERROR=17), `Log→body.stringValue`, pod/container/node→resource attrs. Then **structured** = full LogRecords; **plain** = `strip.py` keeps only `body.stringValue`; **structured-no-trace** (the THESIS-3 isolation condition) = OTLP envelope with `traceId`/`spanId` dropped. **Mandatory scrub:** `trace_id` appears verbatim in the body too, so `strip.py` must strip it identically from the body in plain + structured-no-trace, or the ID leaks.
- **How Drain gets enough volume.** It will be the weak arm — accept and pre-register it. Use the full set of per-minute Train Ticket windows across both dates for template extraction + a `LogisticRegression` window baseline; report template count and base rate as descriptive. If a reviewer demands high-volume Drain scale, keep **LogHub HDFS as a separate Drain/scale/envelope-tax aside** (see next section) — *not* as a trace arm.

**Effort:** low. The only build is `nezha.py` (CSV loader + per-minute windowizer + `fault_list.json` join + `csv→OTLP-JSON` map + the body trace_id scrub). No agent, no Logback MDC, no collector exporter, no live run.

## Does this change the LogHub/Nezha/OTel lineup from DATA_SOURCE_B.md?

**Mostly no — it tightens it.** DATA_SOURCE_B already named Nezha primary and demoted LogHub to a Drain/scale/envelope-tax baseline. The new single-app constraint **hardens** that:

**Final lineup under the single-app constraint:**
1. **Nezha — Train Ticket ONLY → THE single primary app for all three methods** (Drain + in-context + RLM). This is the one change vs. DATA_SOURCE_B: pin to one *system*, not "Nezha" generally, so the single-app constraint is honored (and verified to hold per-system).
2. **LogHub HDFS → KEEP as a separate, descriptive Drain-scale + envelope-tax aside ONLY.** It is *not* the same app, so under a *strict* single-app reading it cannot be a benchmark arm — but the constraint is "ONE app must serve all three methods," which Train Ticket does. LogHub stays as an **out-of-band descriptive baseline** (established Drain F1 ≥0.85, per-line envelope-tax `tokens(structured)−tokens(body)`, scale), explicitly flagged: its synthetic trace_id is constant-per-window (one block = one trace), so `extract_trace_ids()` is a no-op — **never** a trace-navigation arm. If the stakeholder reads single-app as *global* (no second source at all), **drop LogHub** and absorb the envelope-tax measurement into Nezha's per-line variants.
3. **Patched OTel Demo → optional native-OTLP fallback**, built only if a "genuine OTel envelope, not CSV-mapped" arm is demanded. Not load-bearing.

## Risks & live-verification gates

Verified-from-data (no live step): 100% trace_id coverage, many concurrent multi-pod traces/window (Train Ticket ~53-137, ~7-8 pods/trace), exception/return ERROR logs, metric faults zero ERROR logs, zero fault-name leakage in bodies. Remaining gates before trusting the run:

1. **RLM context-crossover (the make-or-break gate).** Measure tokens per per-minute window (~25k records is large) and confirm at least one condition **exceeds the RLM context budget (~2¹⁴ tokens)** so in-context is forced to chunk and RLM navigation is non-vacuous (REVIEW RLM-3). If Train Ticket windows sit below the chunking cap, in-context never chunks and the RLM win is structurally dominated.
2. **`trace_id` population rate** is already verified at 100% for Nezha — but assert it survives the `csv→OTLP-JSON` round-trip (severity→`severityNumber`, ns timestamps, resource attrs) and that `strip.py` plain output is information-equivalent except envelope+IDs.
3. **Concurrent-trace density per window** — re-confirm on the *exact* windows used for the eval split (sampled values were 53-137; pre-register a minimum, e.g. ≥30 distinct multi-pod traces/window).
4. **Drain template stability + label balance** — confirm Train-Ticket-alone yields ≥50 `exception`+`return` windows/class after a **group-aware (episode-keyed) split** (no episode spans train+test, LEAK-5), and that a `LogisticRegression` Drain baseline beats majority-class (the binding question for whether Drain is "weak-but-workable" vs. starved).
5. **Normal-window balance** — confirm `construct_data` (fault-free phase) supplies enough NORMAL windows to control the anomaly base rate (LEAK-3).
6. **`<parse_fail>` rows** — verify the windowizer retains rows whose body JSON fails to parse with their `TraceID` column still populated.
7. **(Fallback only, if OTel Demo is built)** Live coverage probe asserting non-empty `trace_id` per service/flag (especially Java-agent ad/fraud and .NET cart/accounting), confirm patched `logger.Error` sites emit trace-correlated ERROR LogRecords (THESIS-6), and **measure actual lines/min + distinct-template count under high `LOCUST_USERS`** — do *not* rely on the static call-site counts (the "6 zero-log services" claim was **refuted**; only `frontend` is genuinely app-log-silent).
